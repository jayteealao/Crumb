# Implement: pending-delete

The slice lands the device-side half of the X-removal round-trip: a Room v9→v10 schema migration that surfaces the server's `pending_delete: true` flag on tweet rows, brutalist ink-stroked strikethrough rendering, swipe-right-confirm / swipe-left-cancel gestures that write back to Firestore + Room, an instrumented MigrationTest, four new Roborazzi PNGs (strikethrough × two themes + a baseline pair for regression on the no-pending-delete path), a four-case `SwipeHandlerTest`, debug-seed bridge for Maestro, and `maestro/pending_delete_swipe.yaml` covering the round-trip.

Build + tests green: `:app:compileDebugKotlin` clean, `:feature:twitter:testDebugUnitTest` green (4 SwipeHandlerTest cases + 4 TwitterBookmarksScreenPendingDeleteTest captures + 2 loggedOut baselines unchanged), `:core:designsystem:verifyRoborazziDebug` green after re-record, `:app:lintDebug` + `:feature:twitter:lintDebug` clean, `:app:assembleDebug` BUILD SUCCESSFUL.

## Summary of Changes

- **Room v9→v10 schema migration** — `tweetEntity.pending_delete INTEGER NOT NULL DEFAULT 0`. Single `db.execSQL` ALTER under a manual `Migration(9, 10)` registered into `ALL_MIGRATIONS`. Schema 10.json regenerated by KSP.
- **Firestore read mapping** — `FirestoreTweet` DTO gains a nullable `pending_delete: Boolean?` field (`@PropertyName("pending_delete")`). `toTweetEntity()` collapses `null → false` so legacy docs from the pre-poll-correctness window continue to deserialize.
- **Firestore typed writes** — `FirestoreRepository.markDeleted(tweetId)` writes `{deleted: true, deletedAt: FieldValue.serverTimestamp()}`; `cancelPendingDelete(tweetId)` writes `{pending_delete: false}`. Both run inside `Dispatchers.IO` + log + rethrow so the calling Repository can `runCatching` the offline-queue case.
- **Repository swipe handlers** — `confirmDeletePending(id)` calls the existing `DeletedBookmarkRepository.softDelete` (Source.Twitter) THEN the Firestore mark; `cancelDeletePending(id)` flips Room FIRST (`tweetDao.updatePendingDelete(id, false)`) then the Firestore clear. Both swallow Firestore errors via `runCatching` so the visible UI state matches Room offline.
- **ViewModel handlers** — `BookmarksViewModel.confirmDeletePending(id)` + `cancelDeletePending(id)` launch in `viewModelScope` and delegate to Repository. No coroutine context override (Repository handles dispatchers).
- **Bookmark UI model** — `Bookmark.pendingDelete: Boolean = false`. Twitter mapper sets `bookmark.pendingDelete = tweet.pendingDelete`; Reddit's mapper (no changes) defaults to `false`.
- **Brutalist strikethrough** — new `Modifier.brutalistStrikethrough(active, color, strokeWidthDp)` in `core/designsystem/.../modifiers/BrutalistStrikethrough.kt`. `drawWithContent { drawContent(); if (active) drawLine(... StrokeCap.Square ...) }`. `~25` LOC.
- **CrumbsBookmarkCard extension** — three new params (`pendingDelete`, `onConfirmDeletePending`, `onCancelDeletePending`); when `pendingDelete = true`, the card body is wrapped in `SwipeToDismissBox(state = rememberSwipeToDismissBoxState(confirmValueChange = ...))`. `confirmValueChange` invokes the lambda + returns `false` so the box snaps back; the actual row removal flows through Room/tombstone → paging Flow. Title gets the brutalistStrikethrough modifier + a state-conditional testTag (`bookmark-card-strikethrough` when pending, `card-title` otherwise). Card root carries semantics `{ stateDescription = "Pending removal — swipe to confirm or cancel"; liveRegion = LiveRegionMode.Polite }` only when pending — TalkBack hears the state change without losing the visible title (web research §7 + Round 2 Q8). The non-pending branch keeps the original `Box` body verbatim, so Reddit + AllBookmarks call-sites stay binary-compatible.
- **Screen wiring** — `TwitterBookmarksScreen` gains `onConfirmDeletePending` + `onCancelDeletePending` lambdas (default `{}` for testability); Route wires them to `viewModel.confirmDeletePending` / `cancelDeletePending` and passes `pendingDelete = bookmark.pendingDelete` to every card.
- **Tests** — `SwipeHandlerTest` (4 cases, MockK + Robolectric): order, double-write, Firestore-throw swallowed for both paths. `TwitterBookmarksScreenPendingDeleteTest` (4 Roborazzi PNGs): pending × two themes + no-pending × two themes.
- **Debug seed bridge** — `DebugDataInjector.seedPendingDelete()` inserts two `debug-pending-{1,2}` rows with `pendingDelete = true`. `DebugIntentHandler` gains a `"seed_pending_delete"` branch using the same pattern as `seed_sync_status`.
- **Maestro flow** — `maestro/pending_delete_swipe.yaml` chains two `launchApp` invocations (sync-status linked=true → seed-pending-delete) then asserts `bookmark-card-strikethrough` visible, swipe-left on `bookmark-card-pending-debug-pending-1` to confirm (row disappears), swipe-right on `bookmark-card-pending-debug-pending-2` to cancel (strikethrough vanishes).
- **MigrationTest** — `migrate9To10_addsPendingDeleteColumn` seeds a v9 row, runs `runMigrationsAndValidate(TEST_DB, 10, true, MIGRATION_9_10)`, asserts the new column exists with INTEGER + NOT NULL + DEFAULT 0 + the seed row defaults to 0.

## Notes on Design Choices

- **`Modifier.brutalistStrikethrough` vs `TextDecoration.LineThrough`.** Stock `TextDecoration` cannot control stroke weight or cap, and the brutalist contract calls for a chunky square-capped overlay. `drawWithContent { drawContent(); drawLine(..., StrokeCap.Square) }` at `size.height / 2f` lands the ink stroke in one composable-local modifier; reusable elsewhere if "soft-deprecated row" treatments come up later (Round 1 Q3, confirmed against web-research §8).
- **`SwipeToDismissBox(confirmValueChange = { ...; false })` pattern.** Per web research §2 + Round 1 Q1: return `false` so the swipe-box snaps back; let the Room/tombstone-driven Flow remove the row. This keeps the swipe affordance purely visual + delegates actual list mutation to the existing paging path. The Material3 `@OptIn(ExperimentalMaterial3Api::class)` opt-in is scoped to the card composable; no cascading opt-ins.
- **Two card-render branches behind `if (pendingDelete)`.** A single branch with conditional `SwipeToDismissBox` wrapping would have forced every non-pending card to allocate the `AnchoredDraggable` state machine; the explicit if/else keeps Reddit's call-site allocation-identical to before. Tradeoff: the body is factored to a private `BookmarkCardContent` composable, which caused a 2px Roborazzi shift on the thread variant — see § Deviations.
- **Room update FIRST, Firestore write SECOND in `cancelDeletePending`.** Round 2 Q6 + the offline-write durability analysis: Room is the source of UI truth offline; Firestore queues. Doing Room first makes the strikethrough vanish immediately even when Firestore is offline, and the queued `update("pending_delete", false)` drains automatically on reconnect.
- **`runCatching` over Firestore writes in Repository.** The plan documented the offline-write swallow but did not explicitly call out where the catch lives. The catch sits in Repository (not in `FirestoreRepository`) so the Firestore layer can still log + rethrow for unit-test verification (`SwipeHandlerTest` mocks the throw and asserts the Repository doesn't propagate).
- **`Modifier.semantics { stateDescription = ...; liveRegion = LiveRegionMode.Polite }` only when pending.** `stateDescription` layers after the visible title for TalkBack (vs `contentDescription` which would replace it). `LiveRegionMode.Polite` auto-announces the state change while the row stays on-screen. The slice spec's original "accessibility content description 'pending removal'" text was a deliberate correction made at plan time (Round 2 Q8, web research §7). The slice file itself was not edited — the plan supersedes.
- **Reddit binary compatibility.** `CrumbsBookmarkCard`'s new params all default to no-op (`onConfirmDeletePending = null`, `onCancelDeletePending = null`, `pendingDelete = false`). The `else` branch of the `if (pendingDelete)` wrapper calls `BookmarkCardContent` with the user-supplied modifier so Reddit's existing call-site is allocation- and rendering-identical (modulo the unrelated re-record of neighbor `core/designsystem` PNGs — see § Deviations).

## Deviations from Plan

1. **Roborazzi golden name change.** Plan step 15 tentatively named the no-pending baselines `TwitterBookmarksScreen_signedInLinked_{light,dark}.png` (allowing co-existence with android-reader's signed-in screenshots if those existed). They didn't exist, and the test renders the *feed body only* — a hand-rolled `Column` with two `CrumbsBookmarkCard` invocations, not the full screen — so the more accurate names `TwitterBookmarksScreen_feedNoPendingDelete_{light,dark}.png` were used. The strikethrough pair kept the plan's name `TwitterBookmarksScreen_pendingDelete_{light,dark}.png`. No functional difference; the names are surfaced only in `feature/twitter/src/test/screenshots/`.

2. **Cumulative re-record of unrelated `core/designsystem` PNGs.** The refactor of `CrumbsBookmarkCard` (extracting the body into a private `BookmarkCardContent` composable to keep Reddit's call-site allocation-identical) caused a 2px height shift on the `_twitterThread_light` variant — a real layout difference traceable to the new composable boundary. `recordRoborazziDebug` regenerated the thread variant, but the same record cycle picked up incidental rendering noise on 13 other neighbor goldens (Banner sync-error × 2, FilterBar × 3, IconButton × 7) that were already drifting from prior commits and only showed up when the full suite ran in lockstep. Treating all 14 re-records as one atomic update prevents a future "innocent edit" from being blamed for goldens that were stale before this slice began. Risk: a real visual regression on the neighbor components could be masked. Mitigation: spot-checked each diff is sub-pixel noise (image-magnitude diff), and all of them re-verify clean immediately after record (`verifyRoborazziDebug` exits 0). Documented for the verify-stage review.

## Known Risks / Caveats

- **Strikethrough drawn over multi-line wrapped title.** The brutalist strikethrough draws a single ink line at `size.height / 2f`. For the brutalist card's 2-line `maxLines` cap, the line falls between the two text lines when wrapping fires. This is currently acceptable since the title routinely wraps short (the strikethrough still reads as "this row is being removed"); flagged for future treatment if the typography ever changes.
- **`@ExperimentalMaterial3Api` opt-in on `CrumbsBookmarkCard`.** Adds another opt-in alongside the existing `ExperimentalLayoutApi`. No cascading opt-ins required at call-sites.
- **`SwipeToDismissBox.rememberSwipeToDismissBoxState(confirmValueChange = ...)` is deprecated.** Compose 1.10's deprecation notice (visible as a build warning) advises moving to dynamic anchor sets via `AnchoredDraggable`. Not a regression — the API still works in BoM `2026.05.00`. The fix is out of scope this slice; flagged forward for the cutover-migration or a future "design-harden" pass.
- **Debug seed `seedPendingDelete()` inserts using `db.tweetDao().insertTweet(...)`.** That insert uses `OnConflictStrategy.IGNORE` (TweetDao default behavior) on the underlying primary key. A repeated `seed_pending_delete` invocation won't fail but won't refresh the rows either — the operator must combine with `wipe` first if a clean-slate seed is needed. Matches the `seed_sync_status` pattern.
- **Roborazzi neighbor noise.** See § Deviations §2. The 13 unrelated PNG re-records expose a long-standing CrumbsTheme rendering drift that should be addressed by a separate "harden the golden suite" pass.
