### MIG-01: Schema hash drift — `5.json` identity hash does not match known-good 4→5 delta [HIGH]

**Severity:** HIGH | **Confidence:** High

**Location:** `app/schemas/com.github.jayteealao.crumbs.db.AppDatabase/5.json:4` vs `4.json:4`

**Issue:**
The v5 schema JSON records `identityHash: "21c8e471c121d8f64cdd9d59dde7f300"` but multiple entity definitions changed their `notNull` annotation representation between v4 and v5 in the JSON (e.g., `tweetEntity.inReplyToUserId` drops `"notNull": false`; `twitterUser.profile_image_url` drops `"notNull": false`; etc.). These changes are **cosmetic** at the SQLite level (the `CREATE TABLE` SQL strings are identical), but they alter Room's internal identity hash. If a device running v4 upgrades to v5, Room will compare the stored hash `318795277c1859db9a508ff1f07ecb38` against the compiled v5 hash. As long as `MIGRATION_4_5` is registered and runs, Room re-stamps the hash at the end — this is fine. **The risk is that the cosmetic metadata drift is invisible to `MigrationTestHelper.runMigrationsAndValidate` with `validateDroppedTables=true`**, so a future schema error could be silently masked. This is HIGH because a second schema edit after this branch lands could introduce a real hash mismatch that is hard to diagnose.

**Evidence:**
- v4 `tweetEntity.inReplyToUserId`: `"notNull": false` present  
- v5 `tweetEntity.inReplyToUserId`: `"notNull"` key absent (Room serialises nullable differently in newer versions)
- All `CREATE TABLE` SQL strings are identical between v4 and v5 for these tables — no actual column definition change occurred.

**Fix:**
Confirm the v5 schema JSON was regenerated by Room's annotation processor (not hand-edited). If the project was compiled with a different Room version than the one used to produce v4.json, regenerate v4.json from a clean build at that version so both schemas are consistent. Add a comment in the migration noting the cosmetic JSON format change.

### MIG-02: `MIGRATION_4_5` — no down/rollback migration [MED]

**Severity:** MED | **Confidence:** High

**Location:** `app/src/main/java/com/github/jayteealao/crumbs/di/DatabaseModule.kt:142-153`

**Issue:**
`MIGRATION_4_5` only adds a new table (`deleted_bookmarks`). There is no registered down migration. For a mobile app this is standard (Room does not support automatic rollback), but the new table holds deletion tombstones that are critical to the soft-delete feature. If a user downgrades to an apk that does not know about v5, Room will trigger `fallbackToDestructiveMigration` (if enabled) or crash. Since `fallbackToDestructiveMigration` is **not** set in `DatabaseModule`, Room will throw `IllegalStateException` on downgrade, which is correct behaviour — but it is undocumented.

**Fix:**
Add a code comment to `MIGRATION_4_5` explicitly documenting that: (a) no rollback path exists, (b) downgrade will result in Room throwing rather than silently destroying data, (c) any future migration that drops `deleted_bookmarks` must first drain it.

### MIG-03: `pollIds` and `mediaKeys` tables — FK column missing index [MED]

**Severity:** MED | **Confidence:** High

**Location:** `app/schemas/com.github.jayteealao.crumbs.db.AppDatabase/5.json` — `pollIds` and `mediaKeys` table definitions

**Issue:**
`pollIds.tweetId` has a FK to `tweetEntity.id` but **no index** on the FK column. `mediaKeys.tweet_id` similarly has a FK to `tweetEntity.id` with no index. This was present in v4 and is carried forward unchanged into v5. Deletes from `tweetEntity` or JOINs via these FKs will trigger full table scans. This is a pre-existing debt but is confirmed not fixed in this migration.

**Evidence (from 5.json):**
```json
{ "tableName": "pollIds", "indices": [], "foreignKeys": [{"columns": ["tweetId"], ...}] }
{ "tableName": "mediaKeys",  "indices": [], "foreignKeys": [{"columns": ["tweet_id"], ...}] }
```

**Fix:**
Add to a future migration (or create MIGRATION_5_6):
```sql
CREATE INDEX IF NOT EXISTS `index_pollIds_tweetId` ON `pollIds` (`tweetId`);
CREATE INDEX IF NOT EXISTS `index_mediaKeys_tweet_id` ON `mediaKeys` (`tweet_id`);
```

### MIG-04: Firestore backfill — `uploadTweet` is NOT fully idempotent for sub-documents [MED]

**Severity:** MED | **Confidence:** Med

**Location:** `feature/twitter/src/main/java/com/github/jayteealao/twitter/data/firestore/FirestoreRepository.kt:187-242`

**Issue:**
`uploadTweet()` checks whether the **tweet** document already exists before uploading:
```kotlin
val existingTweet = db.collection(TWEETS_COLLECTION).whereEqualTo("tweetId", tweetId).get().await()
if (!existingTweet.isEmpty) { return@withContext }  // skips entire upload
```
This prevents the tweet document from being duplicated, but if a previous upload was **interrupted mid-batch** (e.g., network failure after the tweet document was written but before users/metrics/media were committed), re-running `uploadTweet` for that `tweetId` will see the tweet already exists and **skip the entire batch**, leaving the sub-documents (users, metrics, media, includes) absent from Firestore. The Firestore data will be partially written with no way to recover without manual intervention.

**Additionally**, `uploadTweets()` wraps each call sequentially without atomic outer transaction, so partial failure in a batch leaves Firestore in an inconsistent state.

**Fix:**
Change the idempotency guard to check all sub-documents independently, or use a Firestore transaction that either writes everything or nothing. The simplest safe fix is to change the guard to use `set()` with merge semantics instead of skip-on-exists, or restructure Firestore documents to be self-contained.

### MIG-05: `syncFromFirestore` — order assignment is non-deterministic across re-runs [LOW]

**Severity:** LOW | **Confidence:** Med

**Location:** `feature/twitter/src/main/java/com/github/jayteealao/twitter/data/Repository.kt:79-104`

**Issue:**
When `syncFromFirestore()` runs, it fetches `tweetDao.getMaxOrder()` and assigns incrementing order values to Firestore-sourced tweets. This means the same tweet fetched in two different sync runs could receive different `order` values (e.g., if `getMaxOrder()` changes between runs because new tweets arrived). While duplicates are avoided by the `localIds` check, the ordering is fragile — `order` also affects display sequence, and tweets injected from Firestore will appear at the top of the list regardless of their original chronological position.

**Fix:**
Use the tweet's `created_at` timestamp to compute `order` relative to existing tweets, not a raw counter appended to `getMaxOrder()`.

### MIG-06: `MigrationTestHelper` constructor form may trigger `AbstractMethodError` on Room 2.8.x [NIT]

**Severity:** NIT | **Confidence:** Low

**Location:** `app/src/androidTest/java/com/github/jayteealao/crumbs/db/MigrationTest.kt:17-20`

**Issue:**
The test uses the two-argument `MigrationTestHelper(instrumentation, AppDatabase::class.java)` constructor. In Room 2.7+ this constructor was deprecated in favour of the three-argument form that accepts a `DatabaseDriver`. With Room 2.8.4 (as configured in this project), if the kotlinx-serialization version used by Room's test helper conflicts with the one on the test classpath, this constructor can throw `AbstractMethodError` at runtime — a known issue tracked upstream. This does not affect the migration SQL logic itself but may block CI test execution.

**Evidence:** Room version pinned at `2.8.4` in `gradle/libs.versions.toml:room = "2.8.4"`.

**Fix:**
If `AbstractMethodError` is observed in CI, migrate the test to the newer `MigrationTestHelper` API or pin Room test artifacts to a known-compatible combination. This is low-priority until it manifests.

## Rollback Analysis

- **Reversible migrations:** 0 (Room/SQLite does not provide automatic rollback)
- **Irreversible migrations:** 1 (MIGRATION_4_5 — table drop on rollback would lose tombstones)
- **Risk:** The `deleted_bookmarks` table holds soft-delete tombstones. Losing it on a hypothetical downgrade would cause soft-deleted bookmarks to reappear. This is acceptable for a mobile app without OTA rollback, but should be documented.

## Recommendations

1. **Immediate (HIGH — MIG-01):** Verify v5 schema JSON was produced by the Room annotation processor at the same Room version used in production builds. Regenerate if hand-edited.
2. **Before next migration:** Add FK indexes for `pollIds.tweetId` and `mediaKeys.tweet_id` (MIG-03).
3. **Firestore (MED — MIG-04):** Fix partial-upload idempotency by changing `uploadTweet` to use merge semantics or wrapping sub-document writes in a Firestore transaction.
4. **Documentation (MED — MIG-02):** Comment the no-rollback contract on `MIGRATION_4_5`.
5. **Order assignment (LOW — MIG-05):** Use tweet timestamp for ordering Firestore-sourced bookmarks.
6. **Test infra (NIT — MIG-06):** Monitor for `AbstractMethodError` in CI with Room 2.8.4 and migrate test helper constructor if needed.
